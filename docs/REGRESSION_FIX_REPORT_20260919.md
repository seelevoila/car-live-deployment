## 1. READY 后首音频不能稳定小于等于 3 秒

**现象**：切换或首次使用克隆音色后，点击播报需要约 3 到 7 秒才有声音。

**实测**：相同未缓存测试句中，steady 首次 3403 ms、张首次 3635 ms、遐蝶首次 5948 ms。明确把遐蝶 profile 切好后，21 字真实首段仍为 3356.2 ms；`cache_hit=false`、`prompt_retry_count=0`。加入当前首段预生成并重启最终代码后，同一句正式播报首字节 59.2 ms，响应头 58.9 ms，且 `cache_hit=true`。

**根因**：权重切换和引用准备曾落在首次播报路径；即使权重已准备好，`checked` 仍必须等第一整段合成和验收后才能返回响应头。

**修法**：选定音色、进入直播页/数字主播页、导入或生成新稿、手工改完稿件、改变语速时，使用正式播报的相同 profile、参数和守卫预生成当前第一段。准备期间禁用播放，接口只有在所需首段通过检查并进入生产缓存后才返回 `ready=true`。

**验证**：最终部署态的预生成请求耗时 6400.3 ms，其中包含从 base 切至遐蝶及首段完整检查；随后点击路径首字节为 59.2 ms。该结果证明等待已移到 READY 之前，不证明冷生成已缩短到 3 秒。技术链路满足 READY 后小于等于 3 秒；普通浏览器的最终交互体验仍需用户实际操作确认。

## 2. 长文本首句随句长变慢，长文本偶发停顿

**现象**：较长首句明显拖慢首音频，后续句间偶发较长停顿。

**实测**：profile 已预热后，一条三句稿件的首句约 49 字，响应头/首字节为 6945.1/6946.1 ms，总请求 10549.9 ms。三句均 `cache_hit=false`、重试 0、无 prompt 回退；第一句合成音频时长 7.610 秒。

**根因**：`checked` 路径按完整句子执行“合成 → 音频检查 → 放行”。本次长句没有重试，因此这 6.946 秒不能归因于重试或权重切换。后续若发生重试，每次还会增加一次完整句合成。

**修法**：本轮只把当前第一段提前生成，保留现有自然断句、守卫和阈值；没有把长句强行截成更短片段，也没有关闭检查。

**验证**：第一段在 READY 后可立即命中，但未缓存的长句生成仍随长度增长。后续长句和未预生成稿件仍属于设计限制，尚未修复；需实现带句边界标记的检查/播放协议后再优化，不能用本轮首段缓存结果代替。

## 3. 边播边改稿响应变差

**现象**：修改尚未读到、但靠近当前播放位置的文本时，新内容生效偏晚。

**实测**：前端后续请求仍以 `STREAM_BATCH_UNITS=5` 发送；一旦该批已有声音可听，`revise()` 为避免截断当前语义片段，会把批内修改的应用点推至 `currentBatchEnd`。自动化测试确认未来未播放音频可以取消，当前可听片段不会被硬切断，但本轮没有取得真实直播间的编辑到生效毫秒分布。

**根因**：一个网络流覆盖最多五个可见语句，而前端拿不到后端每个已检查句子的明确边界。为避免截断，当前只能保留整个已开始播放的批次。

**修法**：本轮未修改该策略。首段预生成缩短开始播放等待，但不改变正在播放批次的改稿边界。

**验证**：现有改稿自动化回归通过；用户所述响应变差未完成真实计时验收，状态为已定位、未修。后续需要后端输出逐句边界/序号，再让前端只保留当前可听句并撤销批内未来句。

## 4. 克隆音色首次约 7 秒、第二次约 1 秒，句间停顿长

**现象**：克隆音色首次播报明显慢，随后同句很快；连续播报时有长停顿。

**实测**：遐蝶首次未缓存 5948 ms，重复缓存命中 73 ms。单独执行 selection-time prime 为 3173 ms，下一次首 PCM 为 72.8 ms。最终完整首段预生成实测 6400.3 ms，正式播放首字节 59.2 ms。长稿三句均未重试仍需 10.550 秒完成。

**根因**：首次路径叠加全局权重切换、参考准备、首句完整合成与守卫；重复请求复用缓存。句间停顿还受后续整句缓冲影响，并不总是 prompt 重试。

**修法**：权重、参考和当前首段都移至选择/准备阶段；保留重试守卫和音频检查。

**验证**：首次点击等待已在受控 API 实测中移出播放路径。后续句间停顿尚未解决，不能把首段 59.2 ms 扩展解释为整篇播报已流畅。

## 5. 所有音色听起来像同一个音色

**现象**：切换音色后，多种音色呈现相同的声学特征。

**实测**：构造 `_ACTIVE_MODEL_PROFILE=versatile-xiandie`、再从 9881 外部切到 base 后，旧代码对遐蝶 prime 在约 704 ms 内直接返回，9881 仍驻留 base。修复后同一实验的 prime 用约 3273 ms 将实际权重切回 `versatile-xiandie/round3.pth`。逐音色核对结果：三个内置音色和张实际使用 base；遐蝶实际使用 round3。

**根因**：后端把 `_ACTIVE_MODEL_PROFILE` 当作真实状态；9881 被重启、外部切权或与后端生命周期不一致时，内存缓存会失真并跳过权重核对。

**修法**：同步和异步合成/prime 每次都读取 9881 `/runtime/status` 并比较实际 GPT/SoVITS 路径；只有实际路径一致才跳过切换。`/api/tts/status` 增加实例 ID、实际 GPT/SoVITS 路径及参考缓存统计。

**验证**：新增 stale-profile 回归测试并通过；外部切权后可自动恢复目标权重。该验证证明权重路由恢复，不能单独证明用户主观音色相似度。

## 6. 生成话术和知识库检索失败

**现象**：后端曾报“检索模型尚未安装”，前端生成话术/检索回答失败。

**实测**：清理后缺少 `models/rag/reranker/model_quantized.onnx`，日志出现 `ModelUnavailable`。仓库三分片大小为 94,371,840、94,371,840、90,557,397 字节。用户提供的 `C:\Users\seele\Desktop\rag-assembly-test` 完整模型已直接复制到当前项目：embedding 24,010,842 字节，SHA256 `15b717c382bcb518ba457b93ea6850ede7f4f1cd8937454aa06972366cd19bcc`；reranker 279,301,077 字节，SHA256 `dd98f3e67837d23210a6b7550c08cced4f61845b940ac45be3565840a10f3244`。

**根因**：完整 reranker 是本地生成文件，清理时被删除；旧启动入口没有先校验/恢复 RAG 模型。GitHub 分发方式与本地运行文件被混为一谈。

**修法**：当前项目直接使用用户提供的两个完整 ONNX。三个启动入口在后端启动前运行同一 manifest 校验；完整文件存在时直接使用，缺失时才从仓库分片装配。文档移除错误的 Git LFS 要求，明确“GitHub 用分片、本机用完整文件”。

**验证**：本地模型校验通过；`/api/query` HTTP 200，返回欧拉 5 EV 2026 款 480 km/580 km 续航信息；`/api/script/generate` HTTP 200，provider 为 `llm-grounded-rag` 并返回 137 字稿件。`/api/rag/status` 重启后仍为 ready。

## 7. 内置三音色清理后语调不自然

**现象**：三个内置音色在清理后听感变差，且与“生成专属音色”按钮无关。

**实测**：六段内置参考 WAV 均存在，时间戳和 catalog 采样参数未变；三个内置音色 profile 均为 base。保留了同一句、同一 energetic 参考在错误 round3 与正确 base 下的直接音频：两者均 245,804 字节但 SHA256 不同。F0 摘要也不同：base 的 pitch span 1.629 st、turn count 4；round3 为 2.239 st、turn count 9。

**根因**：配置和参考文件没有变化；失真的 profile 内存缓存允许实际权重与目标音色不一致。对照音频证明不同权重确实生成不同波形和韵律数据，但是否完全解释用户听到的“不自然”仍需要人耳确认。

**修法**：使用问题 5 的真实运行时权重核对；内置音色请求会确认实际驻留 base 后才合成。未修改内置采样值。

**验证**：错误/正确权重对照音频位于 `artifacts/regression-weight-ab-20260919/`；实验后运行时已恢复 base。技术路由已经验证，三个内置音色的主观自然度仍待用户在普通浏览器听测，不能写成听感已修复。
