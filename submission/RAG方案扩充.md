### 2.5 BGE模型深度解析

#### 2.5.1 BGE模型架构

**BAAI/bge-small-zh-v1.5**：
- 基座模型: BERT-base架构
- 参数量: 33M (small版本)
- 训练数据: 中文检索语料 + 问答对
- 特殊设计: 
  - CLS token作为句子表示
  - L2归一化保证向量在单位球面
  - 对比学习训练，正负样本对齐

**模型规格对比**：

| 版本 | 参数量 | 维度 | 速度 | 准确率 | 推荐场景 |
|------|-------|------|------|-------|---------|
| small | 33M | 512 | 快 | 良好 | 中小规模✓ |
| base | 102M | 768 | 中 | 优秀 | 大规模生产 |
| large | 326M | 1024 | 慢 | 最佳 | 极致准确率 |

**为什么选择small版本**：
1. 汽车知识库规模约2000条，small已足够
2. CPU推理延迟18ms，用户无感知
3. ONNX量化后仅90MB，部署友好
4. 在汽车垂直领域测试达到100%准确率

#### 2.5.2 BGE查询优化技巧

**官方推荐的查询指令前缀**：

**效果提升**：

**文档端不加前缀**：


#### 2.5.3 BGE Reranker原理

**交叉编码器 vs 双塔编码器**：

| 特性 | 双塔(BGE Embedding) | 交叉(BGE Reranker) |
|------|-------------------|-------------------|
| 架构 | 独立编码query和doc | query+doc拼接输入 |
| 速度 | 快(可预计算doc) | 慢(每对都要推理) |
| 精度 | 良好 | 更高 |
| 用途 | 召回阶段 | 重排序阶段 |

**Reranker工作流程**：
```
Input: ("这款车续航多少", "综合续航610km NEDC工况")
       ↓
  [CLS] 这 款 车 续 航 多 少 [SEP] 综 合 续 航 610km NEDC工况
       ↓
  BERT交叉注意力机制
       ↓
  相关度分数: 0.95 (原始logit)
       ↓
  Sigmoid归一化: 98%
```

**为什么需要重排序**：
- 双塔召回可能把"续航"和"轴距"都召回（向量相近）
- Reranker能理解query和doc的深层语义关系
- 实测提升准确率3-5个百分点

### 2.6 分块策略详解

#### 2.6.1 父子分块设计

**传统分块问题**：
```
❌ 固定长度分块（如每200字）：
"续航里程：610km\n快充时间：30%-80%需30分钟\n慢充时间"
→ 可能在关键信息处截断
```

**父子分块方案**：

**参数类资料**（如车型配置表）：
```
父块: "充电与续航"类别
├─ 子块1: "综合续航：610km NEDC工况"
├─ 子块2: "快充时间：30%-80%需30分钟"
└─ 子块3: "慢充时间：0-100%需10.5小时"
```

**FAQ类资料**（如话术文档）：
```
父块: "购车优惠政策"章节
└─ 子块: "问：现在购车有什么优惠？\n答：现金优惠5000元，置换补贴最高1万元..."
   (保留完整问答对，不拆分)
```

**分块代码示例**：
```python
def chunk_parameters(text):
    """参数类：按类别分父块，按字段分子块"""
    categories = {
        '充电与续航': r'续航|电池|快充|慢充',
        '动力与能耗': r'电机|功率|扭矩|能耗',
        '空间与车身': r'长度|宽度|轴距|后备厢'
    }
    
    for category, pattern in categories.items():
        if re.search(pattern, text):
            # 每个字段一个子块
            fields = re.split(r'\n(?=[^\s])', text)
            return {
                'parent': category,
                'children': fields
            }

def chunk_faq(text):
    """FAQ类：按问答对完整保留"""
    qa_pairs = []
    # 识别"问："开头的段落
    questions = re.split(r'\n(?=问[：:])', text)
    
    for q in questions:
        if '答：' in q or '答:' in q:
            qa_pairs.append(q)  # 完整保留问答
    
    return qa_pairs
```

#### 2.6.2 分块效果对比

**测试案例**：查询"快充需要多久"

| 分块策略 | 召回结果 | 问题 |
|---------|---------|------|
| 固定200字 | "...慢充0-100%需10.5小时，快充30%-80%需30分..." | 包含无关信息 |
| 按标点符号 | "快充30%-80%需30分钟" | ✓ 精准 |
| 父子分块 | 子块: "快充30%-80%需30分钟"<br>父块: 还能看到"慢充10.5小时" | ✓ 精准+上下文 |

**父子分块优势**：
1. 检索用子块，保证精准召回
2. 生成用父块，提供完整上下文
3. 避免信息截断和丢失

### 2.7 混合检索与融合策略

#### 2.7.1 双路召回原理

**FAISS语义检索**：
```python
# 查询: "这款车省油吗"
query_vector = bge_model.encode("为这个句子生成表示以用于检索相关文章：这款车省油吗")

# FAISS内积检索
scores, indices = faiss_index.search(query_vector, k=24)

# 召回结果（按相似度排序）
[
  "百公里能耗13.5kWh" (0.89),
  "综合续航610km" (0.85),
  "电费成本约0.12元/km" (0.82)
]
```

**BM25词法检索**：
```python
# BM25关键词匹配
query_tokens = ["车", "省油"]  # 分词

# 计算TF-IDF和文档长度惩罚
bm25_scores = [
  "百公里能耗13.5kWh" (12.3),  # 包含"能耗"相关
  "电费成本约0.12元/km" (10.8),
  "动力响应迅速" (2.1)  # 词频低
]
```

**为什么需要双路**：
- FAISS擅长: 近义词（"省油"→"能耗低"）
- BM25擅长: 专有名词（"NEDC"、"kWh"）
- 互补召回，减少漏检

#### 2.7.2 RRF融合算法

**Reciprocal Rank Fusion**公式：
```
RRF_score = Σ 1 / (k + rank_i)
```

其中：
- k = 60 (常数，控制融合平滑度)
- rank_i = 该候选在第i路召回中的排名

**实际案例**：

查询"快充时间"，候选文档A的融合：

| 召回路 | 排名 | 贡献 | 计算 |
|-------|------|------|------|
| FAISS | 3 | 1/(60+3) = 0.0159 | |
| BM25 | 1 | 1/(60+1) = 0.0164 | |
| **RRF总分** | | **0.0323** | 排序使用 |

候选文档B的融合：

| 召回路 | 排名 | 贡献 | 计算 |
|-------|------|------|------|
| FAISS | 1 | 1/(60+1) = 0.0164 | |
| BM25 | 5 | 1/(60+5) = 0.0154 | |
| **RRF总分** | | **0.0318** | 低于A |

**结果**：虽然B在FAISS排第1，但A在两路都靠前，融合后A胜出。

#### 2.7.3 重排序策略

**三阶段Pipeline**：
```
第一阶段: 粗召回
├─ FAISS Top 24 (语义)
└─ BM25 Top 24 (词法)
      ↓
第二阶段: 融合去重
├─ RRF融合得分
├─ 父块去重（同文档片段合并）
└─ 保留Top 12候选
      ↓
第三阶段: 精排序
├─ BGE Reranker逐对打分
├─ 动力范围检查（纯电/混动/燃油）
└─ 最终Top 5输出
```

**动力范围检查**：
```python
# 如果问题明确指定动力类型
if "纯电" in question:
    # 只保留power_type="EV"的片段
    candidates = [c for c in candidates if c.power_type == "EV"]

# 如果问题未指定，使用页面选择的车型
else:
    # 使用当前页面的vehicle_power字段
    candidates = filter_by_power(candidates, current_vehicle_power)
```

**实际效果**：
- 用户问"纯电版续航"，不会返回混动版数据
- 同车系不同动力的配置参数正确隔离

### 2.9 实际检索案例分析

#### 案例1: 近义表达识别

**查询**: "这车耗电吗？"

**分析**：
- 用户口语化表达"耗电"
- 资料中标准表述是"能耗"或"电耗"

**召回过程**：
```
BM25: 未命中（无"耗电"词）
FAISS: 命中✓
  - "百公里能耗13.5kWh" (相似度0.87)
  - "综合续航610km NEDC工况" (相似度0.82)

最终: 正确召回并回答"百公里能耗13.5kWh"
```

**成功原因**: BGE理解"耗电"≈"能耗"的语义关系

#### 案例2: 专有名词精准匹配

**查询**: "支持NEDC工况吗？"

**分析**：
- "NEDC"是专业术语
- 向量可能无法精准表示缩写

**召回过程**：
```
FAISS: 相似度中等 (0.75)
BM25: 精准命中✓
  - "综合续航610km NEDC工况" (BM25=15.2)

RRF融合: 排名第一
```

**成功原因**: BM25词法检索精准匹配缩写

#### 案例3: 动力类型隔离

**查询**: "纯电版的快充时间"

**分析**：
- 知识库包含纯电版和混动版
- 必须正确区分

**召回过程**：
```
初步召回:
  - "纯电版快充30%-80%需30分钟" (power_type=EV)
  - "混动版快充不支持" (power_type=HEV)

动力过滤:
  if "纯电" in query:
      keep only power_type == "EV"

最终: 只返回纯电版数据✓
```

**成功原因**: 业务规则过滤避免配置混淆

#### 案例4: 父子分块上下文

#### 案例5: 资料冲突检测


**成功原因**: 主动识别并标注资料冲突
